# Notifications: periodic producers (PR #527)

Existing signed QStash tick and event wakeups remain unchanged:
`{"job":"labhub-notifications","version":1}`

New fixed signed body, same production endpoint:
`{"job":"labhub-notifications-periodic","version":1}`

This body first runs the existing queue recovery and Chamados workflow dispatcher, then ReservaLab (laboratory/tablet), pending-user approval producers and one due inventory check. It does not scan on a ticket event. Queue and durable dedup are shared; if a producer creates new work a second bounded worker pass is invoked. Failures return 503 with per-producer results; one producer's exception does not suppress the other. New periodic path never falls back to an unscoped global reservation or direct synchronous Push. Reservation reminders expire at start time; pending-user notifications recheck the pending profile and active super-admin recipients at delivery.

## Private bell invalidation (migration 123)

A successful INSERT into public.app_notifications sends a content-free version hint to eligible personal topics. Receive-only Realtime RLS restricts each topic to its active account. The authenticated HTTP API is still the source of content; Web Push stays independent. Connected clients skip redundant 10-second polls and reconcile after five minutes without a successful read; disconnected clients retain ten-second recovery, plus visibility and online events. No production guarantee until the migration and authenticated device tests pass. The periodic approval producer now uses the existing atomic notification_create_with_outbox RPC to persist the admin-only bell entry and Push event together, deduplicated by applicant/week. Tablet and inventory events now persist an idempotent bell row from the existing worker after applicable delivery checks, without creating a second outbox. The GET API checks current campus memberships, workspace role actions and explicit overrides for these operational rows; a failed authorization query returns 503, never bypasses a deny. A successful authorized server window reconciles periodic rows in the personal cache (the latest 50 candidate rows, prefiltered by coarse user/campus audience before the database LIMIT, currently bound the window). Lab spreadsheet reminders now also persist in-app after strict source revalidation. Delivery uses the canonical reservation identity and current campus configuration, never the global fallback; fetch/parse failures retry, confirmed missing or changed reservations are discarded. Per-worker successful snapshots are reused for at most 30 seconds. Both reservation producers use the actual upcoming time window including midnight; tablet reads are limited to this window. Existing non-periodic Chamados local alerts are unchanged. Legacy bell cache is no longer adopted: new reads and local dismissals use authenticated account namespaces; old stock.notifications sync is disabled. Read/dismiss state is device-local, not cross-device.

Managed rollback-only SQL smoke test: supabase/migrations/tests/123_app_notifications_private_invalidation_checks.sql. It requires two existing active QA profiles; never create accounts or send a committed test notification through it.

The bell API now caps recent rows at 50 and orders deterministically. Read IDs are persisted separately in the account's IndexedDB namespace and restored on re-ingestion; local ticket-open and SLA alerts remember their logical event identity even after dismissal. The sheet marks displayed unsnoozed alerts after one second with stable ID dependencies. This is device-local; old unowned legacy cache cannot be safely adopted and no cross-device receipt migration is introduced here. Genuine new events with distinct IDs remain unread; server-side per-user receipt synchronization is a follow-up.

Strict periodic lab scanning bypasses the legacy cache to distinguish source failure from cancellation. This may add spreadsheet downloads compared with the old cached path; monitor runtime and external traffic before switching the production QStash schedule. Existing reminder rows are historical after delivery (subsequent cancellation does not retract a Push already sent).
